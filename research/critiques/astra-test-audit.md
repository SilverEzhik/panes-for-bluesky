# Adversarial audit of test evidence

Reviewed 2026-10-15. Scope: read-only inspection of tests, fixtures, scripts, reports, and relevant application control flow. No new test run or source change was made. This report is the only authored artifact.

## Completion judgment

The evidence supports a working, unusually well-exercised prototype of a sliding Bluesky PWA. It does **not yet support completion of a faithful 2010 native interaction recreation or robust everyday account use**. The distinction is concrete: successful sheet endpoints, scrolling, public API reading, and offline shell loading are demonstrated; transition interruption, historical motion/visual equivalence, cursor pagination, realistic auth expiry, and account races are not.

The recorded run contains 52 successful project executions, eight intentional skips, zero unexpected failures, and zero flaky outcomes (`research/verification/browser-tests.json`). This is 20 scenarios repeated across engines, with four Chromium-only scenarios, rather than 52 independent user journeys. I independently recomputed all 314 baseline file digests: every current file matches `browser-inputs-before.json`. The after report also records the same input set. This strongly supports source stability during the evidence collection. It does not bind the running server's served bundle to those inputs: `reuseExistingServer: !process.env.CI` can attach to an existing process without rebuilding. That is an evidence limitation, not a finding that this run used stale assets.

## Evidence that deserves credit

- `tests/touch.spec.ts` uses the Chromium touch input pipeline for vertical scrolling, header dismissal, pinch, and two-finger pull. The scroll assertion observes actual scrollTop; the panel assertion observes actual removal. These are substantially stronger than calling handlers.
- `tests/trackpad.spec.ts` includes Chromium's synthesized mouse-source pinch and checks visualViewport scale remains one. Ordinary wheel scrolling is also exercised through Playwright's browser input API.
- `tests/video.spec.ts` serves actual HLS segments from HTTP, measures advancing playback time and dimensions, and distinguishes native HLS from MediaSource. The real HTTP fixture appropriately avoids WebKit media requests bypassing page routing.
- `scripts/verify-offline-browsers.mjs` actually stops the origin server, then reloads the controlled page at `/panels/` in all three engines. This is genuine shell-offline evidence. The API-failure/IndexedDB tests correctly identify their narrower scope and do not pretend blocked service workers prove shell installation.
- `research/verification/live-smoke.json` records successful public feed/profile/thread/search reading, no page errors, no broken visible images, and no phone overflow. This helps bridge the deterministic mocks to real public responses.

## False-positive paths and missing evidence

1. **The fixture is permissive at the exact point where authenticated integration needs scrutiny.** `tests/fixtures.ts` routes any host matching `**/xrpc/**`, records no URL/query in its request ledger, accepts arbitrary authorization, returns both session endpoints successfully without enforcing refresh/access semantics, and fulfills every otherwise-unhandled POST with `{}`. A wrong service host, wrong subject/repo, accidental delete, malformed notification write, or refresh misuse can remain green. Login assertions verify a Bearer prefix and one post text, not repo identity, like subject URI/CID, token rotation, reply roots, or deletion identity. The real smoke is unauthenticated and does not close this gap. This is a mock contract weakness; it does not prove the implementation makes those mistakes.

2. **Every normal feed response has 30 homogeneous posts and no cursor.** Search has one result; notifications are empty; all requests complete immediately. Pagination UI, cursor advancement, duplicates, partial-page failures, populated notifications, delayed old search results, profile switching, and account-switch races are effectively absent. App generation and authVersion guards exist (`src/App.tsx:154`, `src/lib/bluesky.ts:184`), but tests never make them contend.

3. **Gesture success is mostly tested after settling and away from competing controls.** Helpers wait for the moving class to clear; tests explicitly wait 850 ms after actions. No case interrupts a spring, reverses within an inertial wheel burst, cancels a pointer, loses focus, resizes mid-gesture, adds a second touch during a drag, or checks unintended compatibility clicks immediately after release. Native two-finger success only asserts a dialog/panel exists; it does not assert scroll/zoom stayed appropriate or that the action fires exactly once. The short flick helper sends 18 moves over only 22 px without an explicit time profile, so its release velocity depends on automation timing.

4. **Cross-engine synthetic gesture tests establish recognition logic, not native touch viability.** JavaScript-created PointerEvent/WheelEvent/gesture events have no browser arbitration, capture pipeline, momentum phases, or real default action. `dispatchEvent()` returning false proves preventDefault was invoked, not that browser zoom was prevented. The eight CDP-only skips are legitimate automation limitations and are correctly named. They are neither app failures nor evidence of Firefox/Safari touch success. Desktop WebKit is also not physical iPad Safari.

5. **Faithfulness has no independent test oracle.** Screenshots are saved artifacts, not comparisons against identified native reference frames. Asset assertions check loadability and image counts, not which extracted icon is used, sizing, alignment, original metrics, or relevant state. Panel tests check broad endpoint relations and CSS declarations, not the native spring trajectory, pinning sequence, resistance, hide/show timing, or stacking at intermediate offsets. The REA-derived formula in `panelPhysics.ts` is valuable implementation evidence; observing the code use its own constants cannot independently prove motion fidelity.

6. **Some strong-sounding titles are broader than assertions.** “Persists only tokens” checks absence of the test password, not an allowlist of persisted fields. “Header drag dismisses only its branch” dismisses the newest sheet, so removing an older sheet with descendants is not tested. “Keys and zoom” checks zoom button state/ARIA label, not image dimensions or actual panning at full size. The live thread smoke sees a seeded dateline and no inline error; it does not record a successful thread response or assert newly fetched thread content, so an incomplete view without an error could pass. These should be described at their actual evidentiary strength.

7. **Offline evidence is single-build and split across layers.** Stopped-server tests use an empty mocked feed and assert the shell; saved-account tests block service workers and abort only XRPC. Both are worthwhile, but no test joins installed shell, account snapshots, drafts, hard reload with network unavailable, and successful reconnection. No browser test exercises update discovery/acceptance with two build versions. The VM worker test verifies handler semantics with simplified Cache/Request objects, not actual lifecycle or multi-tab activation.

For reproducibility, the next reported browser run should require a fresh test-owned server or record the served HTML/JS digests alongside the source fingerprint. The current file stability evidence should be retained. Avoid claiming a new pass merely from unchanged source: dependencies, browser revisions, server bundles, and external services are distinct inputs.

I would accept the current evidence for a preview release with explicitly bounded claims: public browsing, basic account actions under mocked transport, demonstrated Chromium gesture paths, and three-engine offline shell operation. I would withhold “finished faithful recreation” until an independent visual/motion reference check and the first four adversarial scenarios above are resolved. This judgment concerns missing evidence, not an invented count of defects.
